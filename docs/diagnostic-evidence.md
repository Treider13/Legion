# Достоверность диагностических отчётов

Аппаратная приёмка и программная проверка формата отчёта — разные результаты.
`test_acceptance_report.py` проверяет только обработку данных. Он не подключается
к плате, не эмулирует шлюз и не подтверждает работу оборудования.

## Статусы отчёта версии 2

Каждая проверка содержит `stage`, `name`, `status`, `ok` и, при необходимости,
`detail`. Статусы: `PASS`, `FAIL`, `ERROR`, `UNKNOWN`, `SKIP`.

- `PASSED`: присутствуют все обязательные этапы E1–E6, все записи имеют PASS.
- `FAILED`: есть FAIL, ERROR или некорректная запись.
- `INCOMPLETE`: нет FAIL/ERROR, но этап отсутствует, пропущен или неизвестен.

Коды завершения приёмки: 0 — PASSED, 1 — FAILED, 3 — INCOMPLETE.
Ошибка вызова программы может завершаться кодом 2. Неуспех записи отчёта или
журнала также не считается успешной приёмкой.

`run_acceptance_and_commit.sh` проверяет полноту и согласованность JSON, а не
только верхнее поле `ok`. Старые отчёты без схемы версии 2 не являются
доказательством полной приёмки для этого скрипта; исторические файлы не удаляются.
Проверка структуры отчёта не является проверкой подлинности измерений.
Счётчики проверяются как целые числа: `false` не заменяет 0, а `6.0` не
заменяет 6. Загрузчик отвергает повторяющиеся ключи JSON и нечисловые константы
NaN/Infinity, чтобы противоречивый файл не получал успешный результат.

## Что известно об оборудовании

Перед аппаратными этапами шлюз должен явно сообщить `ok=true`, `fake=false`,
`legion=true` и распознанный тип платы. Отсутствующие данные дают UNKNOWN;
эмулятор или отсутствие интерфейса Legion дают FAIL. При таком результате
аппаратные этапы не запускаются.

Для watchdog требуется успешный ответ и булево поле `wd_fired`. Отсутствующее
поле, строка или число не означают исправность защиты. Даже корректное поле
подтверждает телеметрию регистра, а не физическое отсутствие сигнала на выходе.

Текущий `ping` шлюза содержит только `ok`, `fake`, `board`, `legion`.
Он не содержит измеренный источник загрузки FPGA, серийный номер платы или
идентификатор точного RBF. Поэтому E6 помечает autoload/образ как UNKNOWN даже
после ответа шлюза и ручного перезапуска. `--skip-e6` явно записывает SKIP.
С текущим протоколом полный аппаратный PASSED недостижим: подменять отсутствующие
сведения успешным ping нельзя. Эти данные не добавлены предположениями.

Отчёт сохраняет контрольные суммы своих исходников. Они идентифицируют генератор
отчёта и не являются контрольными суммами прошивки на плате.

## Журналы и программные проверки

HDL-раннер учитывает ошибку процесса и записи журнала, требует итоговый маркер
именно нужного тестбенча и размещает рабочую библиотеку и журналы в отдельном
временном каталоге каждого запуска. Это исправление учёта результатов существующего
раннера; успешный HDL-прогон не является аппаратной приёмкой.

Журналы аппаратной приёмки имеют уникальные имена. Это предотвращает перезапись
файлов, но не резервирует физический стенд: одновременный доступ нескольких
процессов к одной плате этими изменениями не проверен.

При сохранении отчёта Git получает явный список буквальных путей JSON и журнала.
Проверка пустого индекса сама по себе недостаточна: другой процесс может добавить
в него файл позже. Отдельная регрессионная проверка запускает настоящие процессы
Git во временном репозитории. Чужой файл исключён из коммита; при блокировке индекса
конкурирующая команда получает ошибку и может быть повторена после завершения.
Эта проверка не подтверждает отсутствие всех возможных конфликтов Git или гонок
в устройстве. Локальные Git hooks остаются под контролем владельца репозитория.

Проверки служебного ПО без доступа к плате:

```bash
python3 fpga/test/test_acceptance_report.py -v
python3 fpga/test/test_report_git.py -v
```

В них используются входные данные для проверки формата и временные репозитории,
а не ответы эмулятора платы. Они не являются аппаратной приёмкой.

Референсы: [VUnit — проверка результата и кода завершения](https://github.com/VUnit/vunit/blob/11877d4555cfe1cb13e118c5042e9d70487cbe93/vunit/test/suites.py#L239),
[Zephyr — статусы проверок](https://docs.zephyrproject.org/latest/develop/twister/twister_statuses.html),
[Prometheus — доступность источника данных](https://prometheus.io/docs/concepts/jobs_instances/).
Правило обязательности E1–E6 относится к приёмке Legion, а не является общим
правилом Zephyr о запрете всех пропущенных тестов.

Дополнительно: [Git commit --only](https://git-scm.com/docs/git-commit),
[JSON: повторяющиеся имена](https://docs.python.org/3/library/json.html#repeated-names-within-an-object),
[обсуждение CPython о дубликатах](https://github.com/python/cpython/issues/89217).
